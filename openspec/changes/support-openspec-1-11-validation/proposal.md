## Why

OpenSpec CLI 1.11.0 shipped, and the plugin's supported set currently tops out at 1.10.x. Verified by running the real 1.11.0 CLI over the plugin's parity corpus and diffing the two published tarballs' validation-engine source (not by reading release notes), **1.11 is a strict additive superset of 1.10 in the safe direction**: `validate` (default and `--strict`), `list`, `spec show`, `schemas`, and `status --json` produce byte-identical output and exit codes over the shared corpus. Unlike 1.9/1.10 the validation-engine source is **not** byte-identical — but the single functional change makes the CLI *stricter*, never laxer:

- **One new validation rule, `PURPOSE_IS_PLACEHOLDER` (WARNING).** A main spec whose `## Purpose` opens with a `TBD`/`TODO` marker — or still carries the archive-generated placeholder sentence — now emits a `WARNING` on `overview`. Default `valid` stays `true`; under `--strict` it flips to `valid: false`. The pre-existing "purpose too brief" WARNING is unchanged and nothing was demoted. Because the plugin's CLI-absent `BuiltInValidator` fallback has no placeholder rule, it stays *laxer* than the CLI — exactly the never-more-restrictive-than-the-client invariant the parity design requires. So there is **no fallback change and no anchor move**.

The corpus verdicts are byte-identical to 1.10/1.9/1.8 in both modes (default 12/13 valid, strict 9/13 valid; id→valid maps carry the same anchors — default `1.8.0`, strict `1.6.0`), because the new rule fires on none of the corpus specs. 1.11's other additions — batch `status --all`, `show <change> --diff`, an Antigravity adapter directory rename, shell-completion generation, and a transactional `schema init` — are off-model or inert to the plugin and change no contract it parses. Adopting 1.11.x is therefore a **capture-and-declare**, plus a **positive-control lock** on the one new validation behavior. Tracked in the project tracker.

## What Changes

- **Capture a real 1.11.0 CLI parity corpus** under `src/test/resources/fixtures/cli/1.11.0/`: the `validate --all --json` default and `--strict` parity twins (reusing the existing `1.6.0/parity-corpus` markdown as capture input) plus `version.txt`, sanitized of machine-specific paths and telemetry ids. The captures are identical (modulo per-run `durationMs`) to the committed `1.10.0`/`1.9.0`/`1.8.0` twins and are committed as a forward tripwire that the auto-discovering `ValidatorVerdictVersionStabilityTest` picks up with no code change.
- **Lock the one new 1.11 validation rule with a positive-control fixture.** Capture `validate --json` (default and `--strict`) on a placeholder-`## Purpose` spec from the real 1.11.0 CLI — one `WARNING | overview` issue with `valid: true` in default, promoted to `valid: false` under `--strict` — and add a contract test that parses it through the plugin's real validate-output parser and asserts that shape. `PURPOSE_IS_PLACEHOLDER` is the only genuinely new validation behavior in 1.11; the contract-test discipline requires it be pinned against captured real output rather than an inferred shape.
- **Wire the durable version guards (tests only).** Add `1.11.0` to `ValidatorVerdictVersionStabilityTest.FLOOR` so the new corpus is a *mandatory* discovery that fails loudly if a future capture is dropped, and add `1.11.0` to the supported-versions assertion in `CliVersionAtLeastTest`. The default verdict-parity **anchor stays `1.8.0`** and the strict anchor stays `1.6.0` — 1.11 is stricter than, not laxer than, 1.8, so no parity-guard rework and no re-anchor.
- **Advance the single-sourced target version** `openspecTargetVersion` from `1.10.0` to `1.11.0` in `gradle.properties`. This is the top-supported-CLI single source that the ui-smoke workflow derives its install from and that `TargetVersionSingleSourceTest` couples to the fixture corpus — so the property bump and the 1.11.0 fixture capture land together (bumping the property without the corpus reddens `targetVersionHasACapturedFixtureCorpus`).
- **Confirm two-digit-minor ordering holds for 1.11.** 1.11 is again a two-digit minor; the shared numeric comparator `CliVersion.compare` already orders `1.11.0` above both `1.10.0` and `1.9.0` (segment-wise `Integer.compare`, exercised by `CliVersionTest.twoDigitMinor_ordersNumericallyNotLexically` and the `CliVersionAtLeastTest` case). No new comparator wrinkle; the `1.11.0` at-least case makes the property tested rather than assumed.
- **Declare 1.11.x a supported CLI generation** — extend the plugin-core supported-versions contract to include the `1.11.x` line (floor unchanged at `1.3.0`, no ceiling) and add a 1.11-generation scenario stating its additive-but-stricter semantics and the new placeholder-rule handling.
- **Refresh the user-facing docs** (vendor-neutral): `docs/openspec-support.md` (add a 1.11.x line and extend the workflow-availability matrix heading/omit note), `README` (supported-lines sentence), and a `CHANGELOG` entry framed as additive 1.11 support (not weakened validation).
- **Footnote the deliberately-unbuilt 1.11 items.** Batch `status --all`, `show <change> --diff`, the Antigravity adapter directory rename, shell-completion generation, and the transactional `schema init` default-key migration (`defaultSchema:` → `schema:`) are described but not adopted — they are off-model or inert AI-tool / CLI-UX / write-path surfaces the plugin does not drive or parse.

## Capabilities

### New Capabilities

_None._

### Modified Capabilities

- `plugin-core`:
  - **Supported CLI versions and capability preservation** — the supported set gains the `1.11.x` line (floor `1.3.0` unchanged), with a new "The 1.11.x line is a supported generation" scenario stating that the plugin delivers the full 1.10.x capability set with no re-gating; the new `PURPOSE_IS_PLACEHOLDER` WARNING is a client-side *stricter* addition, so the default verdict-parity anchor stays `1.8.0`, the strict anchor stays `1.6.0`, and the CLI-absent fallback (which lacks the rule) stays never-more-restrictive; and the new batch `status --all`, `show --diff`, Antigravity adapter rename, shell-completion generation, and transactional `schema init` are off-model or inert and change no parsed contract. It requires per-generation contract coverage against captured 1.11.0 output — the parity twins the stability guard auto-discovers plus a positive-control lock on the placeholder rule — and a version-floor/at-least assertion including `1.11.0`.

_The `validation` capability is intentionally **not** modified: no rule the plugin's fallback enforces, no severity, no fallback, and no anchor changes. 1.11's new `PURPOSE_IS_PLACEHOLDER` rule belongs to the CLI, makes it stricter, and is captured as a contract fixture — the plugin's own validation behavior contract is unchanged, exactly as the 1.9 task-numbering WARNING was handled._

## Impact

- **`src/main`** — **none.** This is a capture-and-declare plus a positive-control contract lock; no production code changes.
- **Build config** — `gradle.properties` `openspecTargetVersion` `1.10.0` → `1.11.0` (single source; `TargetVersionSingleSourceTest` and the ui-smoke workflow consume it).
- **Tests + fixtures** — add `src/test/resources/fixtures/cli/1.11.0/` (parity default+strict twins + `version.txt` + the placeholder positive-control twin(s)) and a `1.11.0/` section to the fixtures `README.md`; add `1.11.0` to `ValidatorVerdictVersionStabilityTest.FLOOR`; add `1.11.0` to `CliVersionAtLeastTest`'s supported-versions assertion; add a contract test asserting the placeholder rule's captured shape (default `WARNING | overview`, strict `valid: false`).
- **Docs** — `docs/openspec-support.md` (primary; 1.11.x line + matrix heading/note), `README`, `CHANGELOG`. All public / vendor-neutral. `docs/feature-comparison-matrix.md` and other `plugin vX.Y.Z` restatements are **not** touched here — they bump at release-cut (bumping a restatement ahead of `build.gradle.kts` drifts `DocumentationHygieneTest`).
- **No IntelliJ Platform API surface touched** — no 2024.2+ compatibility impact and nothing for the Plugin Verifier; the CLI version floor and the `VersionSupport` config-format axis (pinned at `1.2.0`) are unchanged.
- **Out of scope** — the `no_openspec_root` validate/list parser hardening (still low-exposure and deferred, tracked separately); adopting any off-model 1.11 client surface (batch `status --all`, `show --diff`, the transactional `schema init` write path); and the plugin's own store/workset write-surface flag audit.
