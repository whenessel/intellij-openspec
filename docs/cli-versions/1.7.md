# OpenSpec CLI 1.7 — Feature Delta & Plugin Impact (vs 1.6)

> Every version boundary below was verified from the actual npm tarballs' `dist/` (1.4.1 / 1.5.0 / 1.6.0) and the installed 1.7.0 (`/opt/homebrew/lib/node_modules/@fission-ai/openspec`), cross-checked against the upstream `CHANGELOG.md`. `1.7.0` was published 2026-07-29.

## 1. Summary

1.6 → 1.7 is a **strictly additive superset** on every surface the plugin parses. No command was removed or renamed; the `store`/`workset` model and all coordination JSON shapes are unchanged from 1.5/1.6. The changes are: one new change-metadata field (`skip_specs`), additive `--json` keys (`status`' per-artifact `requires`), new optional config fields (`operations.{apply,archive}.guidance`, global `defaultStore`), a new read-only `instructions archive` operation, and AI-tool skill-generation changes (static `SKILL.md` publish, `.agents` target, Codex skills-only) the plugin does not parse. Support is therefore **safe and additive** — and 1.7.0 became npm `latest`, so it is the default install. The plugin was aligned to it by two 2026-08-05 changes (`honor-change-metadata-strip-and-skip-specs`, `relax-config-validator-over-restrictions`), both backed by captured 1.7.0 fixtures under `../../src/test/resources/fixtures/cli/1.7.0/`.

## 3. Per-feature detail

### 3.1 `skip_specs` change metadata (Introduced)
**Mechanics.** A change's `.openspec.yaml` may set `skip_specs: true`; `openspec validate` then treats a change with **zero delta specs** as valid (a pure refactor/tooling/docs change), instead of the "Change must have at least one delta" error (`dist/core/change-metadata/schema.js`, `z.boolean().optional()`; CHANGELOG PR #1399).
**Plugin assessment.** Supported, read-only. `ChangeMetadata` models `skip_specs` for display/labeling; the built-in validator does **not** emit a "≥1 delta" rule, so it never contradicts the CLI here. Honoring `skip_specs` in the plugin's own file-move archive is deliberately deferred "until a real case appears" — the built-in archive simply has no deltas to sync, and Verify delegates completeness to `openspec status`.
**Consumer how-to.** Add `skip_specs: true` to a delta-less change's `.openspec.yaml`; the plugin reads it without complaint and validate stays clean.

### 3.2 `status --json` `requires` edges + reorder (Introduced/Modified)
**Mechanics.** Each `artifacts[]` entry gains a `requires: string[]` (its dependency edges), and `artifacts[]` + `missingDeps[]` are reordered to schema order (`proposal, specs, design, tasks`). No field removed.
**Plugin assessment.** Additive-tolerant. `ArtifactInfo` has no `requires` field, so Gson drops it (no break), and the plugin keys artifacts by id rather than array index, so the reorder is inert. Deriving the artifact DAG from `requires` (rather than the plugin's list-order inference) is a possible robustness follow-up, not a fix.
**Consumer how-to.** Nothing to do; the tool window's artifact chips and status render unchanged.

### 3.3 `operations.{apply,archive}.guidance` (Introduced)
**Mechanics.** `openspec/config.yaml` may declare `operations: { apply?: { guidance: string[] }, archive?: { guidance: string[] } }` — advisory text injected into the *agent* instructions at apply/archive time (`dist/core/project-config.js`, `OperationConfigSchema`; CHANGELOG PR #1062).
**Plugin assessment.** Tolerated. The plugin's config validator keys only off `schema` and has no unknown-key warning, so `operations` passes clean. Surfacing/injecting the guidance would mean re-implementing the CLI's instruction assembler — an AI-bridge concern outside the IDE surface.
**Consumer how-to.** Declare it in `config.yaml` for terminal/agent workflows; the plugin ignores it without flagging.

### 3.4 `defaultStore` + `instructions archive` (Introduced)
**Mechanics.** A global `defaultStore` sets a machine-level fallback store root; `instructions archive` is a new read-only instruction operation mirroring `instructions apply`.
**Plugin assessment.** Out-of-model. Machine-level store routing and the archive instruction assembler are CLI/agent concerns; the plugin's archive is built-in VFS and doesn't consume `instructions apply/archive`. No plugin surface.

### 3.5 Static skills publish · `.agents` · Codex skills-only (Introduced/Modified)
**Mechanics.** 1.7 publishes workflow skills as static `skills/<name>/SKILL.md` files in the repo (so `npx skills add Fission-AI/OpenSpec` works), adds a generic `.agents/` target, makes Codex skills-only (retiring its legacy custom-prompt files), and renames the Windsurf target to Devin (CHANGELOG PRs #1475, #1303). Skills only **grew** across 1.5→1.6→1.7; nothing skills-related was removed in 1.6 (a common misremember).
**Plugin assessment.** N-A for the plugin's *parse* surface — these are AI-tool skill-generation mirrors. The plugin's only stake is the tracked `.claude/skills/openspec-*/SKILL.md` surface plus gitignored regenerated mirrors, kept current by running `openspec update` (done for 1.7 on 2026-08-06).
**Consumer how-to.** Run `openspec update` after upgrading the CLI to regenerate the workflow skills; unrelated to the plugin's runtime.

## 4. Net plugin impact

**No functional work.** 1.7 is additive; the plugin was aligned by the tolerant `.openspec.yaml` parse (+ `skip_specs` modeling) and the config-validator relaxations, both fixture-backed against real 1.7.0 output. The remaining 1.7 surfaces are intentionally out-of-model. The new optional `config.yaml` fields — `operations.{apply,archive}.guidance`, the record-of-arrays `rules`, and the global `defaultStore` — are tolerated with **no code change** (the reader ignores unknown keys and skips list-shaped `rules`; no validator flags them), a stance now **locked by captured fixtures** so a future change can't silently start being stricter than the client. See the [support matrix](../openspec-support.md#workflow-availability-matrix-cli-13x--17x) for the at-a-glance version×support view.
